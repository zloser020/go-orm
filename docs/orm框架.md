# ORM 框架学习笔记

## 1. ORM 框架概览

ORM 是 Object-Relational Mapping 的缩写，即对象关系映射。它用于在 Go 结构体等语言对象和关系型数据库的表、行、列之间建立映射，让开发者可以通过更接近面向对象的方式操作数据库。

例如，Go 中的用户结构体：

```go
type User struct {
	ID   int64
	Name string
	Age  int
}
```

可以映射到数据库中的 `users` 表：

```sql
CREATE TABLE users (
    id   BIGINT PRIMARY KEY,
    name VARCHAR(255),
    age  INT
);
```

对象与关系型数据之间的对应关系可以表示为：

| Go | 关系型数据库 |
| --- | --- |
| 结构体类型 | 表 |
| 结构体实例 | 一行记录 |
| 结构体字段 | 列 |
| 字段值 | 列值 |

ORM 并不是数据库，也不会取代 SQL。它是在业务代码和数据库驱动之间增加的一层抽象，主要负责生成 SQL、传递参数、执行语句，以及将查询结果转换为对象。

```text
业务代码
    ↓
ORM API
    ├── 构造 SQL 与参数
    ├── 执行数据库操作
    └── 将结果集映射为对象
    ↓
database/sql 与数据库驱动
    ↓
关系型数据库
```

常见的 Go ORM 框架包括 GORM。学习具体框架之前，更重要的是理解 ORM 的通用设计：SQL 构造、元数据解析、结果集处理、事务、关联关系和扩展机制。

### 1.1 ORM 框架的核心

ORM 框架最核心的工作可以概括为两部分：

1. **SQL 构造**

   根据用户调用的 API、模型元数据和查询条件生成 SQL，并将数据作为参数传递，而不是直接拼接到 SQL 字符串中。

2. **结果集处理**

   读取数据库返回的列和值，根据字段名、标签或其他元数据，将结果写入对应的 Go 结构体字段。

例如，用户可能通过 ORM API 表达查询：

```go
var user User
err := db.Where("id = ?", 10).First(&user)
```

ORM 在内部完成的工作大致是：

```text
读取 User 的模型元数据
        ↓
确定表名和列名
        ↓
生成带占位符的 SQL
        ↓
传递 SQL 参数并执行查询
        ↓
读取结果集中的列和值
        ↓
通过反射写入 User
```

对应的 SQL 类似于：

```sql
SELECT id, name, age
FROM users
WHERE id = ?
LIMIT 1;
```

不同数据库使用的占位符、标识符引用方式和部分 SQL 语法可能不同。因此，完整的 ORM 通常还需要通过方言（Dialect）屏蔽数据库之间的差异。

### 1.2 ORM 是什么

ORM 是语言对象与关系型数据库之间的转换工具，主要解决两种模型之间的差异：

```text
对象模型                         关系模型
结构体、字段、对象引用    ←→     表、列、主外键
```

这种差异也被称为对象—关系阻抗失配。典型问题包括：

- Go 字段名与数据库列名的命名方式不同。
- Go 类型与数据库列类型不能完全一一对应。
- 对象之间使用引用表示关系，数据库使用主键和外键表示关系。
- 对象的继承、聚合等表达方式与关系模型不同。
- SQL 返回的是行和列，业务代码希望得到结构体或结构体切片。

ORM 通过模型元数据记录这些映射规则。例如：

```go
type User struct {
	ID   int64  `orm:"column=id;primary_key"`
	Name string `orm:"column=user_name"`
}
```

框架可以通过反射和标签得到：

```text
结构体名 User       → 表名 users
字段 ID             → 列 id，主键
字段 Name           → 列 user_name
```

### 1.3 为什么需要 ORM

不使用 ORM 也可以完成所有数据库操作。Go 标准库的 `database/sql` 已经提供了连接池、预编译语句、事务以及 SQL 执行等基础能力。

直接使用 `database/sql` 时，常见代码如下：

```go
row := db.QueryRowContext(ctx,
	"SELECT id, name, age FROM users WHERE id = ?",
	id,
)

var user User
err := row.Scan(&user.ID, &user.Name, &user.Age)
```

这种方式明确、直接，并且能够精确控制 SQL，但在大型项目中容易反复编写以下样板代码：

- 拼装相似的增删改查 SQL。
- 将结构体字段转换为 SQL 参数。
- 将结果集逐列扫描到结构体字段。
- 维护表名、列名与字段名的对应关系。
- 处理不同数据库之间的语法差异。
- 在多个查询中重复实现软删除、审计和缓存等通用逻辑。

ORM 的价值是将这些重复而琐碎的工作集中到框架中：

```text
没有 ORM
业务代码 = 业务逻辑 + SQL 拼装 + 参数处理 + 结果集映射

使用 ORM
业务代码 = 业务逻辑 + 声明查询意图
ORM      = SQL 构造 + 参数处理 + 结果集映射
```

因此，使用 ORM 的主要目的不是让数据库查询“变得可能”，而是减少重复代码、统一数据访问方式并提高开发效率。

### 1.4 ORM 的优点与代价

ORM 的主要优点是 API 对编程更友好，能够提升常规数据访问代码的开发效率。

#### 1.4.1 优点

- 减少常规 CRUD 中重复的 SQL 和扫描代码。
- 统一模型、表名、列名和字段类型的映射规则。
- 通过参数化查询降低手工拼接 SQL 导致 SQL 注入的风险。
- 可以统一实现事务、软删除、时间戳、钩子和缓存等能力。
- 可以通过方言适配多种关系型数据库。
- 更容易复用查询构造逻辑，并进行单元测试。

#### 1.4.2 代价

- 增加了一层抽象，排查问题时仍需理解最终生成的 SQL。
- 反射、元数据解析和对象映射会带来额外开销。
- 复杂查询可能难以用通用 API 清晰表达。
- 不恰当的关联加载可能产生 N+1 查询问题。
- 框架默认行为可能隐藏查询次数、事务边界和锁等关键细节。
- 过度依赖框架特有 API 会增加迁移成本。

因此，ORM 更适合提高常规数据操作的效率，但不意味着业务代码可以不学习数据库和 SQL。

### 1.5 使用 ORM 性能会更好吗

通常不会。对于同一个数据库操作，直接执行精心编写的 SQL 一般拥有更短的调用路径，也更容易进行针对性优化。

ORM 可能引入以下额外开销：

- 解析结构体和标签。
- 使用反射读取或写入字段。
- 构造 SQL 和参数列表。
- 执行钩子、关联加载和其他扩展逻辑。
- 将结果集转换为对象。

```text
直接 SQL：业务代码 → database/sql → 数据库

ORM：    业务代码 → ORM 构造与映射 → database/sql → 数据库
```

不过，在多数业务系统中，网络传输、数据库执行计划、磁盘 I/O、锁竞争和索引设计通常比 ORM 自身的 CPU 开销更重要。因此不能只根据是否使用 ORM 判断系统性能，而应该观察最终 SQL、查询次数和数据库执行情况。

常见优化方式包括：

- 为查询条件和排序字段建立合适的索引。
- 只查询实际需要的列，避免无条件 `SELECT *`。
- 批量插入或更新，减少数据库往返次数。
- 使用预加载或联表查询解决 N+1 问题。
- 为列表查询设置分页和数量上限。
- 对热点查询使用合适的缓存策略。
- 开启 SQL 日志或链路追踪，定位慢查询。
- 对复杂查询直接提供原生 SQL 能力。

一个实用原则是：

```text
优先保证 SQL 正确且清晰
        ↓
通过数据确认性能瓶颈
        ↓
再优化 SQL、索引、查询次数或映射过程
```

### 1.6 ORM 如何使用缓存

缓存不是 ORM 的必备组成部分。它是一种查询优化手段，适合通过插件、钩子或装饰器等扩展机制接入，而不是与 SQL 构造逻辑强耦合。

查询缓存的基本流程如下：

```text
接收到查询
    ↓
根据 SQL、参数等信息生成缓存键
    ↓
查询缓存
    ├── 命中 → 反序列化并返回结果
    └── 未命中
            ↓
         查询数据库
            ↓
         写入缓存并返回结果
```

写操作还需要处理缓存失效：

```text
INSERT / UPDATE / DELETE
            ↓
         提交数据库事务
            ↓
      删除或更新相关缓存
```

缓存的难点不是读取，而是保证数据一致性。设计 ORM 缓存时需要明确：

- 缓存键如何包含 SQL、参数、租户和分页等信息。
- 缓存结果的过期时间。
- 写操作影响哪些缓存键。
- 事务提交前是否允许修改缓存。
- 缓存不可用时是降级查询数据库，还是直接返回错误。
- 是否允许短时间的数据不一致。

只读、更新频率较低且允许短暂不一致的数据更适合缓存。强一致性要求高、更新频繁或查询组合非常多的数据，使用查询缓存的收益可能有限。

### 1.7 Go ORM 与其他语言 ORM 的差异

一些语言的底层数据库库只提供较基础的连接能力，因此 ORM 还需要自己实现连接管理和会话管理。

Go 的 `database/sql` 已经提供了并发安全的数据库句柄和连接池管理，包括：

- 按需创建和复用连接。
- 配置最大打开连接数。
- 配置最大空闲连接数。
- 配置连接最大存活时间和最大空闲时间。
- 通过 `sql.Tx` 管理事务。

因此，Go ORM 通常不需要重新实现一套物理连接池。它应当复用 `database/sql`，并重点处理 ORM 自己的职责：

```text
ORM 层
├── 模型元数据
├── SQL 构造
├── 方言适配
├── 结果集映射
├── 事务 API
└── 钩子与插件

database/sql
├── 连接池
├── 驱动抽象
├── SQL 执行
└── 事务底层支持
```

这里的“会话”需要区分两种含义：

- **数据库物理会话或连接**：由 `database/sql` 和数据库驱动管理。
- **ORM 查询会话**：用于保存本次查询的模型、条件、排序、分页和事务等状态，可以由 ORM 自己抽象。

ORM 查询会话通常应保持短生命周期，避免不同请求共享可变查询状态而产生数据竞争或条件污染。

### 1.8 ORM 框架面试要点

#### 1.8.1 ORM 框架的核心是什么

核心是 SQL 构造和结果集处理。完整框架还需要模型元数据、方言适配、事务管理和扩展机制。Go 中的物理连接池通常交给 `database/sql` 管理。

#### 1.8.2 ORM 是什么

ORM 是对象关系映射工具，用来在语言对象和关系型数据库的表、行、列之间进行转换。

#### 1.8.3 为什么需要 ORM

不使用 ORM 也可以访问数据库，但需要重复处理 SQL 构造、参数绑定和结果集映射。ORM 将这些通用能力集中起来，使业务代码更多地关注查询意图和业务逻辑。

#### 1.8.4 ORM 的优点是什么

主要优点是 API 对编程更加友好，减少样板代码，统一数据访问规则并提高开发效率。代价是增加抽象、学习成本和少量运行时开销。

#### 1.8.5 使用 ORM 性能会更好吗

一般不会。直接编写 SQL 的调用路径更短，也更容易针对复杂场景优化。实际性能更取决于最终生成的 SQL、索引、查询次数、网络和数据库执行情况。

#### 1.8.6 ORM 如何使用缓存

可以通过插件、钩子或装饰器拦截查询，在查询数据库前读取缓存，未命中时执行 SQL 并回填缓存；写操作在事务提交后使相关缓存失效。关键问题是缓存键和一致性策略。

#### 1.8.7 Go ORM 是否需要自己管理连接池

通常不需要。`database/sql` 已经提供连接池和底层事务能力，Go ORM 应复用它，并专注于 SQL 构造、结果映射和 ORM 查询状态管理。

## 2. 后续学习路线

后续实现一个 ORM 框架时，可以按照以下顺序逐步学习：

```text
database/sql 基础
        ↓
模型元数据与反射
        ↓
SQL 构造器与参数绑定
        ↓
查询结果映射
        ↓
CRUD API
        ↓
事务与 ORM 查询会话
        ↓
方言与数据库适配
        ↓
关联关系、钩子和插件
        ↓
缓存与可观测性
```

每实现一项能力，都应同时关注：

- API 是否清晰，查询状态是否会互相污染。
- SQL 和参数是否正确，是否存在 SQL 注入风险。
- 错误是否完整保留并返回给调用方。
- 空值、指针、自定义类型和数据库类型能否正确转换。
- 并发使用是否安全，事务边界是否明确。
- 是否能够通过日志或测试观察最终生成的 SQL。

ORM 是对 SQL 的工程化封装。学习目标不应只是记住某个框架的链式 API，而是理解一次数据库操作如何从 Go 对象转换为 SQL，再如何从数据库结果恢复为 Go 对象。
